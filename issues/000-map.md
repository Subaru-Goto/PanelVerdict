## Destination

A demo-able, **text-only** PanelVerdict **v1** — the first complete build. The full loop end to end: two headlines + a natural-language target audience in → a Bayesian verdict with reasons out. It covers everything the project needs to count as "done for v1" — a domain-specialised chatbot + advanced RAG (delivered as query translation / structured retrieval over the persona pool) + ≥3 tools + a Next.js report UI + the technical & security pieces — the **panel** running on one cheap model (GPT-5 Mini; the **analyst** uses a separate reasoning model — see [003](003-decide-panel-model-and-provider.md)).

## Notes

- **Domain:** synthetic-panel A/B testing for content/marketing creative. Full product vision lives in `docs/project-idea.md` — treat it as a **living draft**: resolving a ticket may mean editing it.
- **This is an EXECUTION-CARRYING map, not plan-only** (Wayfinder default overridden here). Decision tickets (`wayfinder:grilling` / `wayfinder:research`) resolve open questions; `wayfinder:task` tickets carry the actual **build** through to a demo-able app. Build tickets use a `## Goal` body instead of `## Question`.
- **Skills to consult:** `/grilling` + `/domain-modeling` for decision tickets; `/prototype` where a UI/logic sketch clarifies; the langchain skills for build tickets (langgraph is v2 — see Out of scope); `/research` for research tickets.
- **Bayesian scope for this map:** FLAT binary Beta-Binomial + full posterior report (P(B>A), expected lift + 95% CrI, expected loss, ROPE verdict) + adaptive stopping. Hierarchical and zero-inflated models are OUT (B-era).
- **Vote-schema forward-compat (superseded by [002](002-decide-vote-schema.md)):** v1 vote is a **forced binary {A, B}** (no `neither`), represented as a **variant *reference*** so **multivariate (v2)** is a data change, not a schema change. `neither` + the zero-inflated model are deferred *whole* to B-era — a schema **addition** then, not a rewrite. Votes are **model-blind + positional** with counterbalanced, stored order. (Earlier plan to capture {A,B,neither} from day one was dropped — see 002.)
- **Target:** first complete build in ~2 weeks (≈ 2026-07-30) — a personal milestone, not a hard external gate.

Cumulative findings and measurement lessons across experiments:
[`docs/lessons-so-far.md`](../docs/lessons-so-far.md) — read before designing another
experiment or touching the statistics.

- [Representative sampling: filter traits in SQL, drop the disposition vector](017-representative-sampling.md) — the persona vector is **gone**, and with it the last paid call on the targeting path. Requested trait levels became **score bounds on the trait columns**, read *directionally* (`high` is `> 0.5`, so it admits `very_high` — asking for cautious people must not exclude the most cautious), and the panel is a **uniform draw inside the filter**. Two reasons: the vector re-derived approximately what the columns hold exactly, and top-*n* by cosine returns the extreme tail where a panel needs a spread — one vector carrying all five traits plus demographics also skewed the panel on attributes nobody asked for. Knock-on: the seed now varies **every** draw, so sample stability is measurable for any target, which closes the fog item 007 only narrowed. `personas.summary_embedding` stays for [012](012-build-analyst-chatbot-tools.md)'s free-text `search_personas`; the RAG requirement's unstructured half moves to [018](018-audience-research-knowledge-base.md), where prose is all there is.

Input was over-estimated in the same breath (270 tokens, not 300–370) but is a sixth of the bill. Three things the run settled beyond the headline: the provider's reported `cost` equals the list-price derivation **bit-for-bit on 20/20 votes**, so a pre-flight check has real units; `cached_tokens` read **0 on every vote**, confirming by observation what [prompt-caching.md](../docs/research/prompt-caching.md) had derived from thresholds; and `reasoning_effort=low` **halves** the bill at 44% less latency, deliberately **not adopted** because effort changes what the panel is and both 014's first-position rate and 015's framing sensitivity were measured at the default. A **read timeout still cannot be set** — ten votes give no p99, which is what [010f](010f-budget-guard.md) needs. Trap recorded: langchain's `reasoning={"effort": …}` object silently switches to the **Responses API**, which reports no cost at all.
- [Adaptive stopping: vote in chunks, stop when the posterior is decided](010d-adaptive-stopping.md) — **delivered 2026-07-28.** The pipeline votes in chunks of `VOTE_CONCURRENCY` (25) and stops when the report would already make a call — `max(P_worth_acting_on) ≥ credible_mass` or `P_practical_tie ≥ credible_mass`, the report's own 0.95 — **confirmed at two consecutive boundaries** (`_STOP_CONFIRMATIONS = 2`). That count is simulation-sourced *twice over*: the first simulation's baseline was buggy (it replayed sequential stops into the "no peeking" column, making peeking look free and briefly justifying a no-confirmation design), and the corrected table reversed it — a single crossing false-calls 2.3% of true ties against a real baseline of ~0.03%, two crossings hold it to 0.4%, under the 1.2% the old label rule was accepted at ([adaptive-stopping.md](../docs/research/adaptive-stopping.md), correction on the record). Savings: a true 65/35 stops at ~137 votes (32% of the cap), 70/30 at ~91 (55%). The tie stop is illusory at these settings — `P_tie ≥ 0.95` is first reachable at the cap itself — so equivalence stays cap-priced and the clause remains for generality. An early stop travels as **fact, not shortfall**: `stop_reason` as payload data plus a `reading` notice guarded on panelists going *unasked* (not on vote counts — a final-boundary stop with failed votes aboard left nobody unasked), while failed votes stay a `warning`. The label-agreement machinery (`panel_progress`, `Batch`, `_confirmed`, `_CONFIRMATIONS`) is **deleted**; `rope_verdict` now lives only for `detectable_gap`. 011's narrowing animation re-derives batches from the ordered vote records. The paired real-run measurement (~$0.21) waits for [010f](010f-budget-guard.md), decided.
- [Per-vote cache: exact replay, and resume instead of re-run](010e-per-vote-cache.md) — **delivered 2026-07-28.** Every vote is persisted to an append-only `votes` ledger and read back before the model is asked. The key is **not** the ticket's `(persona, test, order)` triple but the **fingerprint of the question itself** — sha256 over the adapter's `configuration` (model id + vote question + reasoning effort, one attribute on `PanelLLM`) plus the exact request strings — so invalidation is automatic (a changed template, headline, question, or model *is* a new key), `test_id` never needed to become a persisted entity (content is identity; the stored id is the run that **paid**), and the 0.66 order trap can't fire (a swapped order swaps the hashed options). Drop-and-reseed explicitly ruled out: votes are paid, non-regenerable output — `ON CONFLICT DO NOTHING`, no FK to personas so a pool reseed can't cascade. Presentation orders are fixed per chunk *before* the hit/miss split (`collect_panel_votes` accepts pre-assigned orders), and cached votes merge back in panel order with `None` usage entries — nothing downstream can tell a cached vote from a paid one, which is exactly what makes a re-run replay and a broken run resume. Test-retest and resume-after-402 are unlocked, not run — both wait on [010f](010f-budget-guard.md).
- [Budget guard: pre-flight check, graceful 402 stop, and a read timeout](010f-budget-guard.md) — **delivered 2026-07-28.** The first full-scale run (three runs, ~$0.17, 250 paid votes, 0 failures — [first-full-scale-run.md](../docs/research/first-full-scale-run.md)) measured $0.000726/vote (~$0.145 per 200-vote test, ~70 in the cap), which put the ticket in its own "cheaper alternative" regime: no elaborate estimator. Shipped: a warn-and-proceed pre-flight (`GET /key` vs `size × USD_PER_VOTE`, a failure-tolerant check that never refuses — 010e makes partial runs worth having); a graceful 402 (the adapter renames the SDK's generic 402 to `OutOfCredit` so the type name travels, the pipeline stops fanning out at the chunk boundary and notices "top up and re-run to resume", zero votes → HTTP 402 not 502); and the read timeout at 60s, sourced from the measured distribution (~3× the slowest of 250 votes, ~4× p99) instead of the SDK's 600s. The run also proved the cache live (200 votes replayed for $0.00 in 19s, byte-identical) and the stop live (fired at the 50-vote floor), and recorded two findings: position bias saturates on identical options, and the fixed per-chunk order seed leans ~2.6 votes per 200 — a future ticket's call.
- [Decide the partial-run threshold](010b-partial-run-threshold.md) — **no threshold, decided 2026-07-28.** The question dissolved rather than got answered: the four candidate shapes were written when the verdict was a label, and a threshold's job was to stop a thin panel overclaiming — but the overclaiming lived in the label, and [020](020-probability-not-label.md) removed it. Every payload quantity now carries its own uncertainty, and the remaining lines are all *derived*: `detectable_gap = None` below n=5, no unanimous panel under n=5 clearing `credible_mass`, `matched=0` → 422 and `voted=0` → 502 (arithmetic, not thresholds). Any legislated floor would be an unsourced constant. "Mark partial" = the three counts plus notices, no boolean — and the one missing message was built with the decision: a **vote-shortfall notice** worded for its remedy (transient, re-run may recover), distinct from retrieval's (the pool gave what it could). `TargetNotice` → `Notice`, since the list is no longer only about the target. Accepted edge, on the record: unanimous n=5 reaches P=0.966 and gets called — softening that, if wanted, is [011](011-build-report-ui.md)'s presentation judgement.
- [The panel-test pipeline: target description in, verdict out](010c-panel-test-pipeline.md) — **delivered 2026-07-28.** `run_panel_test` joins the four stages in plain Python — `select_panel` → `collect_panel_votes` → `tally_votes` / `panel_verdict` — and `/evaluate` runs it at `settings.panel.size`; `FIXED_PANEL` is out of the product path. Two refusals, mapped by HTTP: an **empty panel is 422** (the target is the problem; the model is never constructed, nothing spent) and **zero votes is 502** (types only in the detail). A partial run returns 200 with the shortfall visible in the three counts — requested / matched / voted — and no threshold invented; that line remains [010b](010b-partial-run-threshold.md)'s. `coverage` and the full notice set travel as data. The ticket's pgvector/pool requirement was stale — [017](017-representative-sampling.md) had removed vectors from this read path, so a plain per-request connection suffices. The frontend deliberately breaks until [011](011-build-report-ui.md) (no `target_description` in the form). The first paid run happened **by accident** (~$0.014 derived; exact figure unrecoverable — the bare script never configured logging, the exact failure 010c warned of); the deliberate 200-vote run recording real cost + latency is still owed, and lands with [010f](010f-budget-guard.md)'s needs.
- [Build the panel evaluation module](008-build-panel-evaluation.md) — a panel votes **concurrently** (25 in flight) and a failed vote costs that panelist and no other: `PanelVotes` carries the records and the failures together, so a caller cannot quietly compute a verdict on a thinned panel while reporting the size it asked for — it has to ignore a field to do that (the tracer endpoint refuses outright; a real panel needs 010's partial-run policy). The load-bearing change is the **order assignment**, which 002 had already flagged as broken — index-parity alternation ties who-sees-which-order to however the panel arrived, and `experiments/design.py` documents hitting exactly that. Now an exact 50/50 split, seeded-shuffled, which matters because the model picks the first-shown option 0.66 of the time. And the one bullet that did *not* ship: **prompt caching cannot fire** — the request is ~300–370 tokens against a 1,024-token minimum ([research](../docs/research/prompt-caching.md)) — which strikes 003's "main cost lever" and left the per-test cost unmeasured, because gpt-5-mini's reasoning tokens bill as output and nothing had ever logged usage — since measured by [010a](010a-vote-usage-instrumentation.md).

- [Task-framing sensitivity](015-task-framing-sensitivity.md) — the verdict is **framing-dependent at the vote level** (38–43% of matched votes flip between questions, against a ~0.21 floor) and **framing-stable at the verdict level** (the openness gradient is identical under all three). `preference` stays shipped, for want of grounds to change it. The larger finding is a **failed validity check**: the panel's strongest, most consistent preference falls on a lever that published field data says does nothing, while the three levers that do move real clicks land at chance — so the panel is **unvalidated on same-meaning copy**, which is the regime real A/B tests live in. [Write-up](../docs/research/task-framing.md).

## Not yet specified

<!-- in-scope fog toward the destination; graduates into tickets as the frontier advances -->

- **Does the panel reproduce *any* published copy effect?** [015](015-task-framing-sensitivity.md) found agreement at chance across three Gligorić levers, but with one sentence pair each — so "the lever" and "that sentence" are confounded and the result removes an assumption rather than settling the question. The sharp version needs several pairs per lever; what is not yet sharp is how many, and whether it is worth running before the Upworthy validation study it is a cheap rehearsal for.
- **Rewriting the stimulus set.** Four of the six headline pairs have no-persona baselines above 0.85 or below 0.10, which compresses the range a manipulation can move through, and the neuroticism pair is saturated at 1.00 outright. Sharp enough to ticket: replace the neuroticism pair and rebalance the rest toward a 0.5 baseline, then re-run. What is *not* yet sharp is whether that is worth doing on its own or only alongside the next thing.
- **Do the traits still work in combination?** The sweep varies one trait and pins the other four at medium; every real persona carries five levels at once, drawn correlated. Two candidate designs — an orthogonal two-way factorial (clean interaction estimates) or a regression over personas sampled from the actual pool (realistic, but the pool's Σ makes the coefficients collinear) — and the choice depends on whether interactions or population-level survival is the worry. Also unaddressed: demographics were held fixed throughout, so nothing is known about whether age, income or education move a vote.

- **Reason clustering** (embed + cluster rationales) — in v1's report, or just a flat reason list? Graduates once the report-UI ticket is worked.
- **LangGraph Server + `useStream` — evaluate as one package at v2 (noted 2026-07-30).** The official React hook does what `use-analyst.ts` hand-rolls — messages/turns, isLoading/busy, thread management, typed tool events — plus `interrupt`, which is exactly the plumbing the `run_panel_test` spend gate wants. But it speaks only to a LangGraph Server deployment, so adopting it is never a frontend swap: the agent moves out of FastAPI into a compiled-once graph (the 012 closures hit their recorded expiry and become `context_schema`), the wire contract becomes the framework's (the fixed-sentence error discipline pinned by `test_error_events_never_carry_model_text` must be re-established inside their protocol), and FastAPI stays for `/evaluate` — two backends. Motivation recorded honestly: the hand-rolled stream state (`patchReply`, partial-line buffering) is real comprehension cost the framework would absorb; v1 keeps it for the owned contract, the tiny surface, and the learning value it already paid out.
- **Interest / lifestyle targeting ("sporty", "gamers", "new parents") — v2, decided 2026-07-27.** This is how real audience targeting is actually phrased, and v1 cannot serve it: a persona carries no activity field, so "sporty" is reported as unmappable (verified live). [006j](006j-persona-summary-embedding.md) dropped `interests` after four designs failed on one thing — an open hobby vocabulary has no per-country ground truth, so either the model's style prior sets the distribution or we invent ~430 weights. The route that *did* solve grounding was national time-use surveys ([006i](006i-leisure-profiles.md)), closed because each country cost a bespoke extraction and nothing showed the field changed a verdict. v2 therefore needs that grounding work, not another generation attempt — and it is the one place a persona vector would earn its keep again.

- **DeepEval / CI scope** — **narrowed 2026-07-27, not closed.** The targeting half graduated into [016](016-translation-accuracy-golden-set.md) (does the prompt return the right filters?), and **judge tooling is the wrong instrument for it**: the output is a typed struct with a known right answer, so checking `min_age == 40` needs `assert`, not an opinion. ## Out of scope

- **LangGraph — deferred to v2 (decided 2026-07-27).** The orchestrator is linear apart
  from the adaptive-stopping loop, and a conditional edge back to a node is a `while`.
  Checkpointing is the one feature v1 genuinely wants, and the per-vote cache serves it
  better (vote granularity, not chunk); fan-out is already a tested `ThreadPoolExecutor`;
  progress streaming is a callback. It is also **not a graded requirement** — those name
  LangChain, not LangGraph. Never installed, so nothing is unwound: [004](004-standup-skeleton-infra.md)
  deferred the dependency to the first ticket needing it, which kept the choice open long
  enough to make it on evidence. v2 should adopt it in [012](012-build-analyst-chatbot-tools.md),
  where a multi-turn tool loop with message history is the idiomatic case — not on a linear
  pipeline. Reasoning in the [010](010-assemble-orchestrator-graph.md) decision.

- **Per-test user-settable ROPE — deferred to v2 (decided 2026-07-27).** Real need,
  wrong time: v1 ships a ±7 default with the band recorded on every verdict and
  `rope_verdict` parameterised, so v2 is API/UI work only. The anti-verdict-shopping
  flow is pre-decided in the [009](009-build-bayesian-layer.md) amendment: set at
  test creation, immutable per test, what-ifs labeled as such.

- **Fixing the same-meaning validity gap — deferred to v2 (decided 2026-07-27).**
  [015](015-task-framing-sensitivity.md) showed the panel produces confident
  preferences uncorrelated with published field effects when two variants mean the
  same thing. Closing that needs external validation against real outcomes (the
  Upworthy study), which is already out of scope here, plus very likely prompt or
  model work downstream of it. v1 ships with the measured caveat carried in the
  report ([011](011-build-report-ui.md)) rather than with a fix.
